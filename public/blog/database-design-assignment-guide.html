Database Design Assignment Guide for Students

A step-by-step approach to designing databases that meet academic standards

July 2026 • 12 min read

By the Sleek Academia tutoring team

menu_bookPart of our Database Assignment Help Guide →

Key Takeaways

  • check_circle Start with requirements gathering -- do not open a database tool until you understand the problem.
  • check_circle Entity-relationship diagrams are the bridge between requirements and schema design.
  • check_circle Normalise to at least 3NF for academic assignments unless instructed otherwise.
  • check_circle Document everything -- your design decisions matter as much as the final schema.

Database design is a core component of most IT and computer science programmes. It is also one of the areas where students lose marks unnecessarily, not because the concepts are difficult, but because the process is rushed. A database assignment typically requires you to move from a written scenario to a fully normalised schema with sample queries and documentation. Doing this systematically makes the difference between a pass and a distinction.

Step 1: Gather and Understand Requirements

Every database design begins with a requirements document -- usually the assignment brief itself. Read it carefully and identify the entities, attributes, and relationships it describes. Entities are the things you need to store data about: customers, orders, products, employees. Attributes are the properties of those entities: customer name, order date, product price. Relationships describe how entities connect: a customer places orders, an order contains products.

Create a list of all nouns in the brief -- these are candidate entities or attributes. Then ask: does this noun represent something we need to store data about? If yes, it is likely an entity. If it describes an entity, it is an attribute. Mark ambiguous cases and resolve them as you build the ER diagram.

Step 2: Draw an Entity-Relationship Diagram

The ER diagram is the blueprint of your database. It shows entities as boxes, attributes as ovals or listed within the entity box, and relationships as lines connecting entities. The relationship cardinality -- one-to-one, one-to-many, or many-to-many -- must be clearly indicated.

Many-to-many relationships require special attention. In a relational database, you cannot directly implement a many-to-many relationship between two tables. You must introduce a junction table (also called a linking table) that sits between them. For example, if a student can enrol in many courses and a course can have many students, you create an Enrolment table with foreign keys referencing both Student and Course.

ER Diagram Tips for Assignments

  • Use standard Chen or Crow's Foot notation -- ask your lecturer which they prefer.
  • Include cardinality labels on every relationship.
  • Indicate primary keys clearly.
  • If your diagram spans multiple pages, use a consistent layout so that relationships are easy to follow.

Step 3: Apply Normalisation

Normalisation is the process of organising your tables to reduce redundancy and prevent anomalies. Academic assignments typically expect normalisation to at least 3NF. Here is what each normal form requires:

Normal Form Requirement Common Violation
1NF Each cell contains a single value; each column contains values of the same type; each row is unique. Storing multiple phone numbers in one column separated by commas.
2NF 1NF + every non-key column depends on the whole primary key, not just part of it. In a table with a composite key (OrderID, ProductID), storing ProductName which depends only on ProductID.
3NF 2NF + no transitive dependency: non-key columns depend only on the primary key. Storing SupplierCity in a Products table when City depends on SupplierID, not ProductID.

When presenting your normalisation process in a report, show each step. Start with the unnormalised form, apply 1NF, then 2NF, then 3NF, and explain what you did at each stage. Lecturers award marks for demonstrating understanding of the process, not just for the final schema.

Step 4: Write the SQL Schema

Once your tables are normalised, translate them into SQL CREATE TABLE statements. Include primary keys, foreign keys with appropriate constraints, and sensible data types. Here is a minimal example for a library database:

CREATE TABLE Member (
    member_id INT PRIMARY KEY,
    first_name VARCHAR(50) NOT NULL,
    last_name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    join_date DATE DEFAULT CURRENT_DATE
);

CREATE TABLE Book (
    book_id INT PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    author VARCHAR(100) NOT NULL,
    isbn VARCHAR(13) UNIQUE NOT NULL,
    published_year INT
);

CREATE TABLE Loan (
    loan_id INT PRIMARY KEY,
    member_id INT NOT NULL,
    book_id INT NOT NULL,
    loan_date DATE NOT NULL,
    due_date DATE NOT NULL,
    return_date DATE,
    FOREIGN KEY (member_id) REFERENCES Member(member_id),
    FOREIGN KEY (book_id) REFERENCES Book(book_id)
);

Notice that the Loan table handles the many-to-many relationship between Member and Book. Each foreign key is constrained to reference an existing row in the parent table.

Step 5: Write Sample Queries

Your assignment will almost certainly require sample queries that demonstrate the database works. Include a variety of query types: SELECT with WHERE filters, JOINs across multiple tables, aggregation with GROUP BY, and subqueries if appropriate. Comment each query to explain what it does.

For the library schema above, sample queries might include:

  • "List all books currently on loan with member names" -- a two-table JOIN
  • "Count how many books each member has borrowed" -- GROUP BY with COUNT
  • "Find overdue loans" -- WHERE with date comparison

Step 6: Document Everything

The documentation is where you justify your design decisions. Explain why you chose certain data types, why you normalised to a particular level, how you resolved many-to-many relationships, and what assumptions you made. A well-documented database design submission demonstrates professional rigour and often earns higher marks even if the schema has minor issues.

Include a section on assumptions. For example: "This design assumes that each member can borrow multiple books simultaneously but that a book copy can only be loaned to one member at a time." Making assumptions explicit protects you from criticism about scenarios your design was never intended to handle.

Frequently Asked Questions

What is the difference between 2NF and 3NF?

A table is in 2NF if it is in 1NF and every non-key column is fully dependent on the whole primary key. It is in 3NF if it is in 2NF and no non-key column is transitively dependent on another non-key column.

Do I need to normalise to 3NF for every project?

Most academic database assignments expect at least 3NF. In industry, developers sometimes denormalise for performance reasons, but for coursework, 3NF is the standard target unless the brief says otherwise.

What tool should I use to draw an ER diagram?

Popular free options include draw.io, Lucidchart (free tier), and dbdiagram.io. Your institution may also provide access to Visio or ERwin.

How do I choose between CHAR and VARCHAR in SQL?

Use CHAR for fixed-length data like country codes (CHAR(2)). Use VARCHAR for variable-length data like names or email addresses. VARCHAR is more space-efficient for most real-world data.
